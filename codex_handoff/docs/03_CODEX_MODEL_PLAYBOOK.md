# Codex 模型与推理强度使用手册

## 默认设置

对于当前阶段，默认使用：

```text
gpt-5.6-sol + medium
```

理由：

- 仓库陌生，任务经常包含多文件、构建系统和工具调用；
- 需要正确性，也需要较清楚的教学解释；
- medium 足以完成大多数探索、计划和小修改；
- 始终开 high 会消耗更多时间/额度，也容易让 Codex 把本该由你思考的步骤全部包办。

## 什么时候用 Sol

### Sol + medium

日常默认：

- 阅读一组相关文件；
- 解释调用链；
- 规划一个小改动；
- 修改 1–3 个文件；
- 写测试；
- 解释报错；
- 生成一份周计划。

### Sol + high

以下情况临时切换：

- CMake、CUDA、链接、ABI、多线程问题；
- 跨越多个模块的调用链；
- bug 无法稳定复现；
- 性能测量边界复杂；
- 需要比较多个设计方案；
- 量化/缓存/调度实验设计；
- PR 最终 review。

### Sol + extra high / Max

只在非常困难且高价值的任务使用：

- 连续两次 high 仍不能定位根因；
- 复杂并发或内存错误；
- 需要综合大量日志、多个分支与多个实验；
- 投稿前审查整套方法或大改动。

不要把 Extra High/Max 当默认档。单纯写函数、改格式、查路径不值得。

## 什么时候用 Terra

推荐 `Terra + medium` 完成：

- 已经有明确验收标准的日常实现；
- 添加小型单元测试；
- 修改参数解析；
- 生成 benchmark glue code；
- 文档与注释；
- 根据已有计划执行局部工作。

当任务已经被 Sol 规划清楚后，可以切换 Terra 实施，以节省使用量。

## 什么时候用 Luna

推荐 `Luna + low/medium` 完成：

- 机械性的文件搜索与分类；
- 格式转换；
- 结构化摘要；
- CSV 字段检查；
- 重复测试样板；
- 根据明确规则批量更新；
- 文档拼写与格式检查。

不要用 Luna 负责：

- 难以复现的 bug；
- CUDA correctness；
- 体系结构判断；
- 研究创新性；
- 多模块重构决策。

## 推理档位速查表

| 任务 | 推荐 |
|---|---|
| 查某个符号在哪里定义 | Luna low / Terra low |
| 解释一个函数 | Terra medium |
| 阅读陌生模块并画调用链 | Sol medium |
| 首次读 Embodied.cpp 全局架构 | Sol high |
| 简单 Python 函数 | Terra medium |
| CMake 首个根因 | Sol high |
| CUDA timing/correctness | Sol high |
| 小型局部修改 | Sol medium / Terra medium |
| 批量生成测试数据 | Luna medium |
| 最终 PR review | Sol high |
| 实验设计与消融 | Sol high |
| 极难并发/内存问题 | Sol extra high/Max |
| 多个独立子任务并行 | Ultra，熟悉后再用 |

## 关于 Ultra

初学前 6–8 周不建议使用 Ultra。

原因：

- 多个 agent 会产生更多结果与分支；
- 你更难判断谁是对的；
- 容易跳过亲自理解仓库的过程；
- 并行修改提高冲突和审查难度。

以后可以把彼此独立的任务并行化，例如：

1. agent A 只读映射 serving 调用链；
2. agent B 只读检查 benchmark；
3. agent C 只读审查测试覆盖。

禁止让多个 agent 同时修改同一模块。

## 每次切换前问自己

1. 任务是否真的困难，还是描述不清楚？
2. 能否先缩小范围？
3. 是否已经提供构建命令、首个报错和复现步骤？
4. 是否需要更强模型，还是需要更好的上下文？
5. 这个任务是否应该由我先亲手做一遍？
